# Android–iPhoneのFIT探索停止の調査

調査日：2026年10月30日（日本時間）。対象はiPhone 16／iOS 26.5.2とOPPO PDRM00／Android 13のローカルDebug版。ユーザー申告は「両方とも相手の端末を探していますのまま」。製品コード・近接しきい値・機種補正・利用中のローカル環境のデータは変更していない。

## 結論と観測

今回観測した停止原因は、**iPhone側がBLE受信強度の近接条件を満たさず、相互報告が揃わないこと**。相手のトークン交換そのものは両端末で成功している。

通常のFIT画面を開いた状態で、実行中のFitControllerと既存の近接診断を読み取り、約2.5秒間隔で4回、合計約8秒間照合した。観測値やトークンは改変していない。

| 確認項目                  | iPhone                  | Android                 |
| ------------------------- | ----------------------- | ----------------------- |
| 入力・通信方式            | native／BLE             | native／BLE             |
| 直近2秒の候補数           | 1                       | 1                       |
| 相手トークン              | 取得済み                | 取得済み                |
| 1秒窓ごとの受信強度中央値 | 2窓とも近接しきい値未満 | 2窓とも近接しきい値以上 |
| 判定                      | searching               | near                    |
| 近接報告                  | 未報告・保留claimなし   | 報告済み・保留claimあり |
| 画面の段階                | searching               | searching               |

4回とも上表の状態だった。サーバーの直近3世代のトークンも、一方だけに相手の指定があり、逆方向の指定とセッション作成はなかった。これは片側報告に対する待機と一致する。安全ID・トークン・ハッシュ・写真・名前・生のRSSIや距離は本記録へ保存していない。

## コードとの対応

- `apps/mobile/src/fit/policy.ts`の開発用初期値は近接−45 dBm、存在−70 dBm、窓1秒、継続2秒。`judge`は各窓の中央値が近接条件を満たすことを要求する。存在条件だけを満たしても近接とはしない。
- `apps/mobile/src/fit/controller.ts`は`judge(this.observations, now, 0, this.policy)`を使うため、機種補正は0。近接判定がなく、以前の保留claimもなければ`reportProximity`を呼ばない。
- `apps/functions/src/services/fit.ts`の`reportProximity`は、相手から自分への報告がなければ`waiting`を返す。片側だけの検知ではセッションを作らない。
- `waiting`はクライアントの探索画面を継続する。未達の近接条件は例外ではなく、探索中に留まる正常な分岐なので、エラーは表示されない。
- 90秒の画面タイムアウトは`matched`・`preview`・`waiting`の段階だけに適用される。`searching`中は30秒ごとにトークンを更新し続けるため、今回の状態では探索が継続する。

今回の観測では本人確認用プレビューより前で止まっている。パズル形状の噛み合わせ判定は双方確認後なので、今回の探索停止を説明するものではない。[5-5c](PHASE5_GATT_LINK.md)の「iPhoneがトークンを取得できない」症状とも異なる。

なお`reportProximity`の一部の例外も、セッション未取得中は画面に出さず再試行する実装である。診断上の改善候補だが、今回のiPhoneには報告呼び出し自体がなく、今回の主因とは区別する。

## 次の単位と未確認

次は、現在の2台について端末の向き・遮蔽・既知の距離を揃え、BLE判定の機種差を調べる。受信強度の差を生む要因（端末の送受信特性、向き、ケース、周囲の環境）の内訳は今回の観測だけでは確定できない。

G-PROXの測定基準を先に確定し、[実機試験計画](PHASE5_DEVICE_TEST_PLAN.md)に沿って近距離と離れた距離の両方を確認してから、機種補正またはしきい値の具体案をレビューする。今回の探索停止を解消するためだけに値を緩める変更は行っていない。BLEで正確な10cmを保証しない。

近接条件が双方で成立した後も、通常画面での相互検知→本人1枚の確認→双方確認→サーバーの成立／形状による不成立を一周する検証は未完了。同OS同士、3台以上、UWBの距離精度・誤接続率も今回の調査では確認していない。

推奨モデル：Claude Code＝Opus 5.5／Effort High、Codex＝GPT-6.1 Sol／High。重点レビューも同じ設定。片側の接続改善と、遠距離・複数候補の誤接続防止を併せて評価するため。

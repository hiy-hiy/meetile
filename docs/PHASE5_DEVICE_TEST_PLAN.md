## 5. 距離試験の手順と観測の定義

距離試験の成功は**盤面結合ではなく、意図した相手の本人ピースが双方に表示されたこと**。片側だけの表示は双方成立に数えない。画面に表示された人工図柄で相手を照合し、名前や内部IDを記録しない。`no-fit`（形状が合わない）は距離失敗に数えない。`already-connected`は前提を満たさないため機能試験へ分ける。

1. 非金属の固定台と定規で配置する。外装の最短間隔を距離と定義し、背面同士・横並びを分ける。UWBアンテナ間距離を直接測った値とは扱わない。ケース・保持方法・手の置き方を同じにする。
2. 一つのseriesは同じ端末、build、方式の期待値、距離、向き、遮蔽、混雑、観測時間で事前に20試行以上と決める。距離や遮蔽を変えたら新しいseriesにする。端末の左右・開始操作順を交互にし、条件の実施順は偏らせない。
3. 両端末のFITを一度停止し、所定の配置で双方が探索を始めた時点を0秒にする。人が2台を操作する時間差は記録誤差として扱う。距離試験は一条件10秒を観測する案。探索中に近づけて成功させない。
4. 双方のプレビューが出たら`preview`、片側だけなら`one-sided`と記録する。相手が違えば`unexpected`と記録して直ちに離脱。意図した相手なら双方表示までの時間を記録する。片側にも表示がないまま観測時間を終えたら`timeout`。セットアップ崩れ・電話などで完了できなかったら`aborted`とし、番号を消さない。中断前にプレビューが出ていた試行を`aborted`で隠さない。
5. 通常の距離反復では最終確認を押さず、プレビュー後に双方離脱する。別の機能試験で双方確認まで行い、`merged`または形状による`no-fit`を確認する。成功後は同じ盤面になるため、以後の距離反復にその状態を使わない。
6. 各試行の終わりに広告・探索・相手表示が停止したことを確認し、新しいトークンで再試行する。トークンの原文・ハッシュ・セッションIDは記録しない。期限・日付の権威はサーバーであり、Macや端末時計を実測のために変更しない。
7. 事前の回数を終える前に良い結果だけで止めない。中断のあるseriesでは率を出さず、原因を機能記録へ残す。再測定は新seriesにし、元のseriesを保存する。集計はseries単位で、方式・端末・距離をまとめた一つの成功率で弱い条件を隠さない。

方式は両端末で観測できたときだけ`ble`／`uwb`を記録する。通常画面に測距方式・RSSIの表示はない。5-5bで追加したローカル開発用の粗い観測表示を使う。混在は実装上BLEの期待値だが、期待値だけで実測方式を確定せず、観測できなければ`unknown`を使う。方式別受け入れでは、両端末の直近観測を個別に確認する。観測表示だけで方式別の実機受け入れを完了としない。生のRSSI／距離を必要とする補正作業も別の単位で、製品ログやサーバーへの送信を追加しない。

## 6. 記録とオフライン集計

```sh
mkdir -p .tools/proximity-measurements
cp docs/fixtures/proximity-session.template.json .tools/proximity-measurements/session.json
pnpm proximity:report .tools/proximity-measurements/session.json
```

テンプレートの試行数は0で、結果を表していない。`evidence: physical`は想定する記録の種別であり、テンプレートを実機確認の証拠とは扱わない。測定前にGPROX-DRAFT-1の採否を決め、決定記録の仮名を`criteria.reference`へ入れる。`approved`は人が決定した後だけ設定する。CLIは申告の真偽や承認の存在を検証できない。

build labelは任意の検証版の仮名（例：`LOCAL-MIXED-01`）。`sourceSha256`には、測定対象のソースを固定したアーカイブのSHA-256を入れる。Git未コミットの現状では版名だけを根拠にしない。秘密設定・写真・資格情報を含めず、少なくとも`apps/mobile/src/fit`・`apps/mobile/modules/proximity`・`apps/mobile/app.config.ts`・lockfileを固定する。生成された`android/build`・`.gradle`などは含めない。各端末の実際のバイナリと起動設定は機能記録へ別途照合し、hashだけでnativeモードを推測しない。設定と実通信の経路を確認してから`nativeModeConfirmed: true`にする。

1試行の記入例（**人工の説明用データ。測定結果ではない**）：

```json
{
  "number": 1,
  "outcome": "preview",
  "peer": "intended",
  "elapsedMs": 4200,
  "methods": ["unknown", "unknown"],
  "multipleDetected": false,
  "merge": "not-attempted"
}
```

`methods`の順序は`deviceIds`の先頭2台。`preview`は双方表示の場合だけ。片側表示は`one-sided`とし、表示した側で確認した相手と時間、両側の方式（未観測はunknown）を記録する。`one-sided`の`merge`は`not-attempted`にする。`timeout`／`aborted`では`peer`・`elapsedMs`・`methods`をnull、`merge`を`not-attempted`にする。片側のみ表示や操作中断の補足も機能記録へ残す。`multipleDetected`は観測時間内に複数端末案内が出たか。`thirdDistanceCm`は3台試験のCの距離。計測方式を観測できない状態でUWB成功と記録しない。

CLIはネットワークや端末へ接続せず、JSONを読んでstdoutへ集計するだけ。build/native/基準申告のない実測、疑似近接の種別、余分なフィールド、重複・欠番、未知の端末、人数不足、観測時間を越える成功を拒否する。エラーでは入力値・ファイルパスを表示しない。入力記録の送信・保存は行わない。

- `complete`は予定した全試行に結果があり、中断がないという意味。機能・機種範囲・合格・信頼性の保証ではない。
- 未完了・中断があるseriesは率をnullにする。未観測方式は`methodsConfirmed: false`にする。率が出ても、方式・誤相手・不足条件の確認は人が行う。
- `intendedPreviewRate`は意図した相手の双方表示率。`anyPreviewRate`は相手を問わず片側または双方に表示した率で、遠距離・3台時の抑止を見る。`oneSidedPreviews`も別に数える。片側だけの意図しない表示も安全上の不具合として機能記録へ残す。
- `noFit`と`merged`は距離の成否から分離する。最大所要時間は意図したプレビューが出た試行だけの値で、timeoutを含む待ち時間の最大値ではない。
- `acceptance`は常に`not-evaluated`。全件が成功に見える記録でも公開・G-PROX・Phase 5完了を自動承認しない。

実測ファイル・詳細記録はGit対象外の`.tools/proximity-measurements/`へ置く。端末の仮名、機種・OS、条件、集計結果だけを必要な実装記録へ転記する。安全ID、認証情報、トークン、MAC、UDID、写真、名前、キャプション、位置、相手関係を入れない。自由記述にも同じ制限を適用する。不要になったローカル記録は試験レビュー後に削除する。補正用の生値が必要なら別途保存対象・期限を決め、追跡用データへ転用しない。

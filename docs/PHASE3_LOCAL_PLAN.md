## 1. 最初のゴール

前回使用したiPhone 16をMacと同じLANへ接続し、次を一周できるようにする。

```text
ローカル検証の説明・年齢区分・任意の署名
  → カメラで人工図形を撮影
  → 撮り直し・キャプション・最終確認
  → Mac内のサーバーへ送信
  → 開発用の審査結果
  → サーバーがピースと盤面を生成
  → Todayに写真入りのピースを表示
  → タップで詳細表示・拡大・移動
```

既存の撮影・状態管理・画像処理・盤面表示を再利用する。最初の到達点は合格の一周。その後、拒否・保留・一時障害・再起動を同じ環境で確認する。

実Firebaseへの配備・課金接続、実際のGoogle審査、外部ユーザーへの配布は行わない。法務文書・保存期間・窓口の確定は並行する課題として残し、この内部検証の前提にはしない。

## 3. 通常版との境界

### 接続先とデータ

- project IDを`demo-puzzle-sns-local`に固定する。既存の実development、staging、productionは使わない。
- iOS／Androidの識別子は`jp.puzzlesns.app.local`、表示名は「puzzle-sns ローカル」とする。既存の開発版とインストール・認証・端末保存情報を分ける。
- 明示的な`APP_MODE=local`を入口とし、`APP_ENV=development`かつDebugビルドでだけ許可する。通常設定の既定値をローカルへ変えず、stagingやReleaseでは拒否する。
- ローカル用の非秘密のネイティブFirebase設定を生成し、SDK・Functions・各Emulatorのproject IDを一致させる。実アプリの登録ファイルや鍵はコピーしない。生成物はGit対象外へ保存する。
- 匿名認証、Firestore、Storage、Functionsを、最初の要求より前にすべてEmulatorへ接続する。設定不足やMac停止ではエラーにし、クラウドへの代替接続は設けない。
- Mac側でも固定project IDと全Emulator hostを検証する。子プロセスへ実認証ファイルやログイン用トークンを引き継がず、ローカル用の生成物で通常の配備物を上書きしない。

demoプロジェクトを使うと、起動していないサービスへの要求が実リソースへ接続されることを避けられる。サービス間でproject IDをそろえる点も公式手順に従う。[Firebase Emulatorのproject IDと接続](https://firebase.google.com/docs/emulator-suite/connect_auth)

### 審査・App Check・初回確認の提案

現在の[Phase 3記録](PHASE3.md)は、Emulatorでも実App Checkを要求し、人工の審査処理を実アプリから選べない方針である。そのままでは、実Firebase・審査サービス・正式文書に未接続の状態で今回の一周を作れない。本計画では、本人の内部検証用ローカル版に限って、次の経路を追加する案を採る。

| 項目           | ローカル版の提案                                                                          | 通常のクラウド接続版                     |
| -------------- | ----------------------------------------------------------------------------------------- | ---------------------------------------- |
| 審査           | Mac内の仮審査。人工図形のみで試す                                                         | 実Vision／Natural Languageと既存ポリシー |
| App Check      | 専用Functions入口では要求せず、クライアントでも初期化しない                               | 現在のApp Check要求を維持。不足時は拒否  |
| 認証・閲覧権限 | Auth Emulatorの匿名認証と既存Rules。未認証の投稿は不可                                    | 現在の匿名Auth・権限検証を維持           |
| 初回確認       | 「内部検証」「実審査なし」「人工素材のみ」「Macに保存」と説明し、年齢区分と検証開始を確認 | 実HTTPS利用文書の表示と正式な同意        |
| 記録           | Emulator内だけに`local-test-v1`として記録。正式文書への同意とは扱わない                   | 正式文書の版本と同意記録                 |

この差分は、別識別子・別接続先・別入口の内部検証経路の提案である。実装に進む際はこの例外も含めて計画を確認する。製品仕様原本と、通常版の実審査・同意・認可の条件は変更しない。

全画面で「ローカル検証・実審査なし」を表示する。ローカルの開始確認に通常の法務リンクは要求せず、正式な利用規約への同意と混同する文言も使わない。既存の確認保存形式を再利用する場合も、demo名前空間と`local-test-v1`に閉じ、通常の版本へ流用できないことを検証する。通常版に仮URLを設定したり、`request.app`を偽造して通常のApp Checkを通したりしない。

### 配備物への混入防止

- サーバーは専用の`index.local.ts`等から別ディレクトリへビルドする。通常の`index.ts`に、環境変数一つで審査や認可を無効化する分岐は加えない。
- ローカル入口はFunctions Emulator内・固定demo project・全Emulator hostがそろう場合だけ動かす。通常環境では起動・要求を拒否する。
- モバイルはJS設定に加えて、ローカル用のネイティブビルド印とDebug判定を確認する。JS設定やOTA更新だけで通常バイナリをローカル版へ切り替えられないようにする。
- 通信実装のモジュールはビルド時にローカル用か通常用かを解決する。実行時の条件分岐だけで両方をbundleへ取り込む設計は避ける。
- 通常のFunctions配備物とモバイルbundleに、仮審査・ローカル入口・データ初期化処理を含めないことを検査する。確認はフラグの既定値だけで済ませない。
- EASへのローカル配布プロファイル追加、インターネット向けの公開、一般利用者への配布は今回行わない。

## 5. ローカル実行環境

初回はMacとiPhoneを同じLANへ接続する前提。実機からは`localhost`ではなくMacのプライベートIPv4を指定する。初回対応はプライベートIPv4とシミュレーター用loopbackに絞り、公開IPや任意URLを接続先にしない。

通常のEmulatorテストとポートが衝突しないよう、以下をローカル専用にする案とする。

| サービス              | ポート案     |
| --------------------- | ------------ |
| Auth                  | 19099        |
| Firestore             | 18080        |
| Storage               | 19199        |
| Functions             | 15001        |
| Emulator hub／logging | 14400／14500 |
| Firestore WebSocket   | 19150        |

実機が使うサービスだけをLANへ公開し、管理用ポートはloopbackに置く。Emulator UIは最初は無効。使用済みポートでは起動を止めて案内し、所有していない既存プロセスを停止しない。

iOSのローカルネットワーク許可・HTTP通信、Androidのデバッグ用HTTP許可をローカル設定だけに加える。通常版へ広いHTTP許可を持ち込まない。署名、Developer Mode、端末の信頼等、本人操作が必要な場面も手順に記載する。

既存の`session.tsx`はインターネット到達性も見ている。ローカル版では、インターネットに出られなくてもMacへ接続できる場合を考慮し、Macとの疎通を確認する。通常版の通信断の扱いは維持する。

既存XcodeでローカルDebugビルドを作り、Expo Goは使わない。ネイティブ設定の変更時は再ビルドする。[Expoのローカルビルド手順](https://docs.expo.dev/guides/local-app-development/)

## 6. 仮審査と繰り返し試験

Mac側で以下を選ぶ。クライアントの送信データに「審査を通す」指定は追加しない。署名・キャプションの入力制限、JPEG形式・サイズ・再エンコード、日付・所有者・同日一枚の検証は実処理を使う。

| シナリオ     | 動作                                             | 確認内容                                               |
| ------------ | ------------------------------------------------ | ------------------------------------------------------ |
| `approved`   | 人工画像を処理し仮の合格を返す                   | 撮影からTodayまでの一周                                |
| `rejected`   | 仮の拒否を返す                                   | ピースを作らず再撮影できる                             |
| `held`       | 仮の保留を返す                                   | 未公開で「確認中」。日付切替後に前日の内容を公開しない |
| `error-once` | 対象画像の処理で一度失敗し、次の再試行で合格する | 同じ入力の再試行で一個だけ確定する                     |

仮合格を自動審査の安全性の証拠にはしない。実審査のしきい値と精度は別作業。シナリオはローカル実行設定だけで選び、保留・拒否を通常の公開APIから変更する機能は作らない。

何度も撮影を試すため、Mac側にローカルデータの初期化コマンドを用意する。固定demo名前空間と自分で起動した環境だけを対象にする。既存の日次制限を弱めたり、通常の写真削除・Gallery作品削除機能としてアプリへ追加したりしない。

初期化では処理中のローカル環境を止め、指定したローカルデータを消して起動し直す。起動ごとの非秘密の実行IDを使い、アプリの次の起動時に初期化を検知して、ローカル認証・本人設定・画像キャッシュをそろえて消す。通常再起動ではデータを維持する。

日付とピース生成はMac側に置く。iPhoneから日付・形状を指定するAPIは作らない。4時境界はサーバー時計を注入する既存の自動試験と、担当段階の実機確認で検証する。

## 8. 完了条件と検証

### 自動検証

- 誤project、host不足、staging、Release、通常バイナリへのローカル指定を拒否する。
- HTTP経由で実Auth Emulatorの匿名トークンを使い、開始確認→日付取得→撮影セッション→画像送信→確定→盤面・画像取得を通す。サービス内部の直接呼出しだけで合格にしない。
- 未認証、他人の撮影セッション、非参加者の盤面・画像取得、正本への直接書込みを拒否する。
- 拒否・保留・一時障害、再送・同時要求・4時越境でも二重ピースや審査前公開が起きない。
- Mac停止・誤接続でクラウドへ切り替わらない。実クラウドやGoogle審査の経路を使わないことも検査する。
- 初期化はローカル以外を受け付けず、通常再起動と初期化後の再起動を区別する。
- 通常のFunctionsは、ローカル設定を渡してもApp Check不足・不正projectを拒否する。通常の配備物とモバイルbundleにはローカル専用処理を含めない。
- 各変更で整形・`pnpm lint`・`pnpm typecheck`・`pnpm test`・`pnpm test:emulators`を実行する。配備物を変更する段階では`pnpm check:functions-artifact`と追加の混入検査も実行する。

### iPhoneでの手動確認

1. 専用アプリ名とローカル表示が見え、Macへ接続できる。
2. カメラ権限、前面／背面、人工図形の撮影・撮り直し、任意の文章入力・最終確認が動く。
3. 仮合格でピース化し、Todayの写真・輪郭・詳細・拡大・移動が動く。
4. アプリ再起動後も同じピースが見え、同日の差替えはできない。
5. 背景移行・Mac停止時に写真が消え、復帰後に再取得する。インターネットに出られないLAN条件も確認する。
6. 仮拒否・保留・一時障害を区別でき、ローカル初期化とアプリ再起動後は新しい試行として撮影できる。

この一周は、実審査・正当なApp Check要求・安全機能・Gallery・BLE／UWBの合格ではない。Androidは設定・自動検査の対象に含め、Android実機の合格は別に記録する。

# Phase 5-5b：開発専用の近接観測

作成：2026年10月30日（日本時間）。対象は[5-5a](PHASE5_DEVICE_TEST_PLAN.md)から引き継いだ方式・停止状態の観測。距離の基準決定・機種補正・G-PROXの合格判定は含まない。製品のFIT条件・サーバー認可・盤面・写真・年齢確認は変更しない。

## 表示と境界

ローカル版の画面上部へ「開発用・近接観測」を追加した。通常のFITと同じfactoryで選ばれた入力を、観測用のwrapperへ通す。UIは入力・粗い状態・直近の方式だけを表示する。

| 表示                   | 意味                                                  | 証明しないこと                                         |
| ---------------------- | ----------------------------------------------------- | ------------------------------------------------------ |
| native／疑似近接       | 実際に選択されたsourceの種類。疑似近接は明記する      | ビルド設定の期待値だけで実通信を確認したことにはしない |
| 未開始                 | まだ観測用の試行がない                                | アプリ再起動前の状態は復元しない                       |
| 開始要求済み・受信待ち | source.startを呼び、観測はまだない                    | OSが広告・探索を開始した保証ではない                   |
| 観測を受信             | 直近の有効な観測が届いた                              | 近い・候補が一人・相互検知した、という判定ではない     |
| 交換・測距待ち         | tokenが未読、かつ距離値なし                           | BLE非対応という意味ではない                            |
| BLE                    | 読み取り済みtokenを伴うBLE観測で、距離値なし          | UWB能力・開始待ち・復帰の原因を確定しない              |
| UWB距離あり            | nativeから有効な距離値を伴う観測が届いた              | しきい値内・FIT成立・物理距離の精度を意味しない        |
| 古い観測・方式未確認   | 最後の観測が1秒より古い。画面の500ms周期で更新        | 受信がないことだけで無線停止を断定しない               |
| 停止要求中             | stopを呼び、応答を待っている                          | 即時の無線停止を保証しない                             |
| 停止処理の応答あり     | nativeが停止処理の呼び出しを終え、Promiseが戻った     | OSの内部処理完了・相手からのアクセス停止は別途照合する |
| 停止の応答未確認       | 拒否・失敗・応答を保証しないsource                    | 停止成功に昇格しない                                   |
| 利用不可・中断         | 既存の権限・Bluetooth OFF・非対応・前面離脱通知を受信 | 距離による不成立とは分ける                             |

画面を読み取る時点ではすでに停止・staleになっていることがある。方式は観測中に記録し、停止後に残っていない値を推測で補わない。片側だけの観測では、双方の方式・GATT・サーバーFITは確認できていない。

コードは`src/local/proximity-observation.ts`の1スナップショットとwrapper、`proximity-observer.ts`の登録・実行時検査、`proximity-diagnostics.tsx`の表示へ分けた。世代で古いstopの応答・古い観測・古い失敗を遮断する。新しい試行とstop時には方式を消去する。アプリ再起動・JS再読み込みでは状態を失う。

スナップショットにはinput・activity・method・既知のreasonだけを持つ。人物ID・一時ハンドル・トークン・名前・写真・生のRSSI／距離を取り込まず、履歴・ファイル・外部送信・ログを作らない。sourceの元の観測は既存判定へそのまま渡し、診断の値をFIT認可の根拠にしない。

## 通常版へ含めない仕組み

`runtime-files.cjs`へ`@puzzle-sns/proximity-observer`を追加。通常版は`src/cloud/proximity-observer.ts`のidentity関数へ解決し、store・UI・ローカル実装をバンドルしない。ローカル版だけでwrapperへ切り替える。

ローカル側でも`__DEV__`、`mode=local`、`variant=development`、ネイティブInstallationの`localBuildEnabled()`をすべて確認する。staging・cloud・Release・通常バイナリでは表示・登録しない。ローカルのReleaseを拒否する既存のMetro制約は維持した。

## 停止の応答

`ProximitySource.stop`は、従来のvoidに加えて停止呼び出しの応答を示す`Promise<boolean>`を扱えるようにした。NativeProximityはstopの失敗をfalseに変換し、未処理のPromise拒否を残さない。同じ試行への重複stopも、その停止応答を返す。FIT側は従来どおり停止を要求し、サーバー処理の正本は変更しない。

AndroidはstopのPromiseをradioキューのcleanup後にresolveする。以前の「キューへ停止を積んだ時点で戻る」応答だけを補った。古いrunIdで新しい試行を止めない条件と、前面離脱時の即時lease無効化は維持する。iOSは既存のmainキュー上の停止処理が戻る応答を使い、Swiftの動作は変更していない。OSはキャンセルを非同期に処理するため、応答を無線停止の物理的な証明とは呼ばない。

## 実機での確認方法

1. [ローカル起動](PHASE3_LOCAL_SETUP.md)を使い、測定対象のビルドとMetroを同じ`PROXIMITY_MODE=native`で起動する。両端末ともローカル版を使う。疑似近接の表示を見落とさない。
2. 通常のFITを行う場合は、開発者本人による開始確認・人工ピース・当日資格を先に揃える。本人の同意を代行したり、診断のためにサーバーの資格を迂回したりしない。
3. 画面上部で未開始→開始要求→交換待ち／BLE／UWB距離ありを確認。相手を検出しない場合にBLE成功を捏造しない。近接判定・サーバー報告・本人1枚・双方確認は通常のFIT状態でも別に確認する。
4. FITから離脱し、停止要求と応答を確認。OSの自アプリ探索カウンター・相手のGATTアクセス停止を照合する。ホーム移動・ロック後は自動再開しないことも確認する。
5. 再読み込みによる未開始への戻りと、前面離脱の通知を区別する。複数端末・UWBの本格的な測定は対応実機と[試験計画](PHASE5_DEVICE_TEST_PLAN.md)の事前基準が必要。

ネイティブブリッジ単体の確認に人工トークンを使う場合も、サーバーのFIT操作や写真を作らない。これは開発用の通信プローブで、G-PROXの距離測定・年齢確認後のFIT一周の代わりではない。プローブは今回の確認用にだけメモリー上で作り、製品ボタン・恒久的なJSグローバル・通常版へのテスト経路は追加しない。終了時に停止・プローブ消去・Bluetoothと起動先の復元を行う。

# アカウントを持たない設計への変更案

作成日：2026年10月12日（日本時間）

状態：設計検討中。正式仕様・実装への反映前。安全要件の衝突は未解決。

## 1. 今回の目的と承認範囲

ユーザーは、日次IDを破棄してもFirebase Anonymous Authの継続するUIDから過去と現在の投稿を関連づけられることを受け、「アカウントを完全に持たない」方向への軌道修正を指示した。写真・作品ごとに独立した閲覧キー・削除キーを端末に残すことは許容すると回答した。

今回の成果物はこの変更案だけ。PRODUCT_SPEC.md、既存の承認記録、実装、Firebase設定は変更しない。公開用IDを日替わりにするだけでは、内部の人物対応表は消えないという説明不足を修正する。

継続する利用者IDをなくすことと、日をまたぐブロック・利用停止の維持は衝突する。後者の扱いはまだ承認されていない。本書はその安全要件を変更する承認でも、外部公開の許可でもない。

## 2. 提案する設計原則

- Firebase Anonymous Authを含む利用者アカウントを作らない。
- 日をまたぐ共通の利用者ID、端末ID、人物単位の公開鍵、全投稿を束ねる所有者レコードをアプリの権限モデルに持たない。
- 当日の操作には、その日に限って有効な参加資格と認可情報を使う。翌日の参加資格との対応は作らない。
- 写真削除・過去作品の閲覧には、対象ごとに独立した権限キーを使う。別の日に作成した写真や別作品へ同じ鍵を使い回さない。一つの対象のキーは、その対象の後日の操作にも使用できる。
- 人物単位の認証をなくしても、閲覧・更新・削除の認可はなくさない。盤面の正本と最終判定は引き続きサーバーが持つ。
- 当日の参加資格、写真の削除権限、作品の閲覧権限を分離する。過去の作品キーで翌日の操作はできない。

これは共通の人物IDによる投稿の束ね直しをなくす提案であり、通信や写真からの関連づけをすべて防ぐ保証ではない。

## 3. 写真削除は「人物の確認」から「その写真の鍵の確認」へ

写真を確定する際、十分な強度を持つ独立したランダムな削除キーを用意する。本人端末はそのキーを安全な領域に保存し、サーバーは写真IDとキーの検証値を保存する。具体的な暗号方式・発行手順は次の設計フェーズで確定する。

例として、写真Aには削除キーA、写真Bには削除キーBを用意する。サーバーに「AとBの所有者は同じ人」という対応表は置かない。

後日、写真Aを削除する際は、写真Aに対するキーの所持を検証する。キーAでBを削除したり、他の写真を列挙したりできないようにする。削除後はキーの用途を終了し、過去・現在の盤面と参加者端末へ写真Aの無地化を伝える。

本人端末の削除キーだけを本人が保持する。キーをDTO・公開URL・近接発信・通常ログへ混入させない。通信の保護、漏洩・リプレイ対策、検証値への総当たり対策を具体化する。

この方式が確認するのは対象写真の削除権限であり、撮影者の実名や生体的な本人性ではない。鍵を失うとこの経路では削除できず、盗まれると権限を悪用され得る。問い合わせと権利侵害対応の経路は別途必要。

## 4. 当日の参加と過去作品の閲覧

### 当日の参加

当日の参加資格に撮影セッション・ピース・FIT・最新盤面を紐づける。日本時間午前4時で操作資格を失効させ、新しい日は独立した資格で始める。Firebaseの匿名アカウントを毎日作り直す方式は採らない。

日付失効は各APIで判定する。保存データの物理削除、TTL、ログ・バックアップの保持は別問題なので、午前4時の失効だけを「全データの即時消去」と説明しない。日次の認可情報をいつ物理削除するかは具体化が必要。

「1人1日1ピース」を物理的な人物単位で厳密に保証することは、この資格だけではできない。当日資格ごとの1ピースと、アプリ再導入・資格再発行への対策を区別し、既存仕様の制限が何を保証するか明確にする。

### 過去作品の閲覧と削除同期

最終盤面は端末に保存する。後日の再取得と写真削除の同期には、作品ごと・閲覧者ごとに独立した閲覧権限を用意する案を検討する。ある作品の権限で別作品を閲覧できないようにする。同じ作品への権限関係は残るが、作品をまたぐ閲覧者の共通IDは作らない。

過去の写真削除が発生した場合、作品の閲覧権限で最新の無地化状態を取得し、キャッシュと表示に反映する。オフライン端末への即時反映と外部書き出し画像の回収は保証しない。

端末から過去作品の権限を一括送信すると、同じ所持者の作品群だとサーバーに分かる。一括の作品一覧取得・全写真削除API・権限同期は新設せず、必要な権限だけを提示する。個別要求でも通信時刻やIP等から推測される可能性は残る。

## 5. 残せる安全処理と成立しない安全処理

| 機能                         | アカウントなしでの扱い                                                           |
| ---------------------------- | -------------------------------------------------------------------------------- |
| 投稿前審査                   | 写真・テキストを対象に継続可能                                                   |
| 写真の通報・運営削除         | 対象ピースと作品の権限を基に設計可能。報告権限・回数制限・証拠保全は詳細化が必要 |
| 本人による写真削除           | 写真ごとの独立した削除キーで設計可能                                             |
| 当日の相手のブロック         | 日次資格を対象に設計可能。過去作品の特定ピースの非表示も可能                     |
| 翌日以降も同じ相手をブロック | 対象を再認識する情報がなければ、新しい資格・写真へ適用できない                   |
| 人物単位の継続的な利用停止   | 翌日や再発行後の参加を同じ主体として識別できず、現在仕様どおりには維持できない   |

「昨日の写真を見えなくすること」と「昨日の投稿者が明日投稿する写真も見えなくすること」は別の機能。前者を後者の代替として説明しない。

App Checkはアプリ・端末の正当性を確認する仕組みで、写真所有者の権限証明や翌日の相手の再認識を代替しない。App Check、IP、端末指紋、プッシュ通知トークンを継続的な人物IDの代わりとして使わない。

AppleのUGC規定1.2は迷惑な利用者のブロック機能を求め、Google PlayもUGC体験に応じたユーザー・コンテンツの通報とブロックを求める。当日の非表示だけでこのアプリの適合が確認できたとは扱わない。プライバシーを保ちつつ必要な安全対応を成立させる方式の検証、または配布・提供形態の再検討が必要。

完全な日跨ぎ非識別を維持する案は、現状では一般公開可能なMVPとして完成していない。安全機能は省かず、解決前に外部ベータを開始しない。内部の設計検証では人工素材を使用する。

## 6. 情報漏洩に対する改善範囲

共通UIDと所有者対応表をなくせば、その対応表から複数日の写真を同一利用者へまとめる経路をなくせる。ただし次の情報から推測できる可能性は残る。

- 写真に写った顔・場所・物、繰り返される署名や文章。
- IP、通信時刻、アクセスログ、監視SDK、鍵の発行・使用記録。
- 当日資格から長期閲覧・削除権限を発行したときの記録と、残ったバックアップ。
- プッシュ通知トークンや端末証明を使い回す通信。
- 端末内に保存されたギャラリーと複数の権限キー。

ログ最小化・保存期間・物理削除・バックアップ・第三者SDKを含めて検証する。運営者に対する非識別、DBだけが漏洩した場合の非識別、端末や通信まで漏洩した場合の非識別を区別する。

## 7. 現行仕様との衝突と実装への影響

正式変更が必要になる箇所：

- PRODUCT_SPEC.md §11.3・§19.4・§25：Firebase Anonymous Authと継続的な安全ID。
- §17.2・§17.3：日をまたぐ利用停止・相互ブロック。
- §14・§18.1・§19.6：所有者照合・参加権限・表示用データと非公開対応。
- §3・§4：一日一枚が保証する単位と再発行への対策。
- §12・§15・§18.2：長期閲覧、通知とデータ・鍵の保存期間。
- IMPLEMENTATION_PLAN.md D-02・D-05・D-06・D-08：本人鍵、長期権限、利用終了・一括削除、再導入時の扱い。
- 将来のApple／Google復元：利用者単位の連携を新方針へ持ち込まないよう再検討。MVPには追加しない。

確認した実装の主な依存：

| 箇所                                     | 現在の依存                      | 変更案の影響                                 |
| ---------------------------------------- | ------------------------------- | -------------------------------------------- |
| apps/mobile/src/native-port.ts           | 匿名ログインとUID別の購読       | 日次資格・作品権限によるAPIアクセスへ変更    |
| apps/functions/src/entrypoints/auth.ts   | Firebase匿名AuthのUIDを要求     | アカウントなしの対象別認可へ変更             |
| apps/functions/src/domain/models.ts      | ownerUid、盤面メンバーUID       | 日次参加資格と独立した対象別権限に分離       |
| apps/functions/src/repositories/paths.ts | UID別状態・権限・ブロックのパス | 人物単位の台帳を除去する構造へ変更           |
| firebase/firestore.rules・storage.rules  | request.auth.uidによる閲覧認可  | 非公開データを保護したまま配信方式を変更     |
| packages/puzzle-engine                   | 認証に依存しない幾何計算        | 基本ルールを維持し、当日の重複判定キーを入力 |

単に匿名ログインを外す変更ではない。Firestore・Storageを公開読み書き可能にして代替しない。サーバーAPIが権限を検証してデータを返す案を基本に、購読・画像配信・コスト・権限失効の方式を具体化する。

## 8. 次の設計フェーズの完了条件

1. 日をまたぐブロック・利用停止と非識別の衝突を解決し、製品ルールの変更点を明示して承認する。未解決のままMVPを公開しない。
2. 日次資格・写真削除権限・作品閲覧権限の発行、保管、失効、再試行、紛失時の扱いを確定する。
3. 新旧の人物対応が残らない移行・消去手順を定める。旧仕様のUIDやACLを残したまま非識別を主張しない。
4. 別の写真の削除拒否、非参加者の閲覧拒否、期限切れFIT拒否、再試行・同時FITの一貫性、過去作品の削除同期を検証する。
5. ログ・DB・SDK・通知・バックアップで日をまたぐ共通キーが残らないかを確認し、保証範囲と例外を記録する。
6. 正式仕様と承認記録を更新した後、バックエンド認可の一つの移行フェーズから実装する。

暗号方式・ストア適合・実機の鍵保管・削除同期は本書で検証済みとはしていない。

## 9. 確認資料

2026年10月12日に以下を確認。権限キーによる変更案は本書の設計提案であり、Firebaseがそのまま提供する完成機能ではない。

- [Firebase匿名認証](https://firebase.google.com/docs/auth/web/anonymous-auth)：匿名アカウントを作成する方式であること。
- [Firebase App Check](https://firebase.google.com/docs/app-check)：利用者認証とアプリ・端末証明の役割の違い。
- [Apple App Review Guidelines 1.2](https://developer.apple.com/app-store/review/guidelines/)：UGCの審査・通報・利用者ブロック・連絡先。
- [Google Play UGC policy](https://support.google.com/googleplay/android-developer/answer/9876937)：体験に応じた継続的なモデレーションと通報・ブロック。

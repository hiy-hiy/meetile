# Phase 5-5d：iPhone–Android混在FIT一周

作成：2026年10月30日（日本時間）。対象はiPhone 16（iOS 26.5.2）とOPPO PDRM00（Android 13）による通常のFIT画面での一周。状態：**近接しきい値をメモリー上で一時的に緩めた条件で、相互検知→本人ピース確認→相手の離脱通知→双方確認→接続成功までを確認した**。現行の開発用しきい値（−45 dBm）のままでは成立せず、しきい値・機種補正はG-PROXの決定へ回す。距離精度・誤接続率・Phase 5の合格判定ではない。

製品の成立条件、コード上の近接しきい値（near −45 dBm、presence −70 dBm、窓1秒、hold 2秒）、サーバー認可・盤面・写真の閲覧範囲は変更していない。

## 実施した内容

開発者本人が両端末で年齢区分・内部検証の開始確認を行い、別々の人工の図柄を撮影して当日のピースを作成した。サーバーでは当日の参加者2人が別々の盤面にいることを確認した。以後、通常のFIT画面から操作した。

1. 最初は両端末とも「人工の相手」とだけ一致した。既存のMetro（8082）が`PROXIMITY_MODE`なしで起動されており、ローカル版の既定である疑似近接になっていた。`PROXIMITY_MODE=native`の別Metro（8083）を起動し、manifestで`simulatedProximity=false`を確認してから両端末を接続し直した。
2. nativeで「FITする」を押すと、開発用観測の表示で描画中の更新エラーが出た（下記の修正1）。
3. 修正後、**相互検知と相手本人のピース表示まで到達した**。両端末に相手の図柄が表示され、図柄は一致した。所要は約48秒で、途中で2台なのに「複数の端末」が表示された（修正2・3）。離脱・最終確認の確認は、この試行では行っていない。
4. 通信の修正後は両端末とも候補が常に1つになったが、FITは成立しなくなった。iPhoneが受けるAndroidのRSSIがしきい値に届かないため（下記）。
5. ユーザーの選択により、ローカル開発版の実行中のメモリー上だけで`nearRssi`を−60 dBmにした（Metro inspectorから`DEFAULT_POLICY`を書き換え。ソースは変更せず、アプリの再起動で−45に戻ることを確認）。すぐに相互検知し、双方に相手の図柄が表示された。
6. iPhoneだけが離脱しても、Androidの画面が変わらなかった。サーバーは両者の`fitViews`を`cancelled`にしていたが、アプリが受信値を捨てていた（下記の修正5）。修正後、アプリを再起動してから再試行し、Androidに「相手が離れました。」が出たことをユーザーが確認した。
7. 続けて両方で最終確認を押し、**接続成功（merged）**。サーバーで同じセッションの両`fitViews`が`merged`、当日の参加者2人が同じ盤面1つになったことを確認した。形状による不成立は今回は発生していない。

## 修正

| 番号 | 内容                                                                                                                                                                                                                                                                                                                                                                               |
| ---- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | ローカル開発用の観測ストアで、`configure`の通知を描画後（microtask）へ遅らせた。FIT画面の`useMemo`内から呼ばれ、別コンポーネントの観測パネルを描画中に更新していた。製品の`FitEntry`は変更していない。修正前に失敗し修正後に成功する試験を追加。                                                                                                                                   |
| 2    | iOS：接続中の相手のトークンが変わった、トークン読み取りが失敗した、相手のGATTサービスが変わった場合は、その接続を切って候補から外す。トークン更新後は新しい一時ハンドルとして扱う（Androidと同じ扱い）。                                                                                                                                                                           |
| 3    | Android：無線の開き直し直後にOSが通知する前回のリンクは、相手からの接続として再利用しない（サービス登録後のリンクだけ）。前回のリンクがOS上で残る相手へは、自分からの接続を最大6秒待つ。                                                                                                                                                                                           |
| 4    | Android：広告の送信出力を既定のMEDIUMからHIGHへ（ユーザーの選択による）。しきい値・機種補正は変更していない。                                                                                                                                                                                                                                                                      |
| 5    | 通常版・ローカル版の`subscribeFit`で、Firestore TTL用の`expireAt`を外してから進捗を渡す。サーバーは`fitViews`へ`expireAt`を付けて書くが、契約の`fitViewSchema`は余分な項目を許さないため、離脱・成立・不成立の通知がすべて捨てられていた。既存試験は`expireAt`のない値を使っていて検出できなかった。サーバーの保存形と同じ値の試験と、ローカル通信層の試験を追加（修正前に失敗）。 |     |

修正2・3の原因：JSは約30秒ごとに新しいトークンでネイティブの無線を開き直す。Androidは開き直すたびに広告アドレスが変わる。一方、iPhoneが張ったLEリンクは更新をまたいで残り、新しい無線がそれをすぐ再利用していた。iPhoneは古いリンクの相手と、新しい広告アドレスの相手（接続できず未読）の2つを見ていた。修正後、Androidだけを開き直す通信プローブでは、iPhoneの候補は2〜4秒の未読を経て新しい候補1つに戻り、2候補が同時に現れなかった。

## 観測したRSSI（ほぼ密着、通常のFIT中）

ネイティブから届く観測を、両端末のJSで一時的に受信して1秒ごとの中央値だけを集計した。生の値・ハンドルは保存せず、確認後に受信処理を外した。

| 条件              | iPhoneが受けたAndroid | Androidが受けたiPhone | 候補数            |
| ----------------- | --------------------- | --------------------- | ----------------- |
| Android広告MEDIUM | −52〜−65 dBm          | −24〜−36 dBm          | 常に1（更新時も） |
| Android広告HIGH   | −49〜−57 dBm          | −30〜−35 dBm          | 常に1（更新時も） |

近接は「相手1台について連続2窓の中央値が−45 dBm以上」で、相互検知には双方の報告が必要。iPhone側が一度も届かないため、報告が出ず一致しない。最初の48秒の一致は、一時的に強い値（接続上の読み直しで−27 dBmなど）が出た偶然とみられる。

これは近接方式の欠陥ではなく、機種ごとの受信感度・送信出力の差。同じしきい値を両方向へ適用する現行の仮値では、この組み合わせのFITが成立しない。しきい値の変更、送受信の機種補正、混在時の補正値の伝え方は、いずれもG-PROXで実測から決める事項で、今回は変更していない。

修正5は5-1／5-2から存在した不具合で、通常版にも影響する。Metroのホットリロードでは、起動時に作られた通信層の関数が古いまま残るため、反映にはアプリの再起動が必要だった。

## ローカルサーバーの異常終了

この作業中にローカルサーバー（Firebase CLI）が2回「An unexpected error has occurred」で異常終了し、Firestoreだけが親を失って残った。

- 1回目（14:56ごろ）は、こちらの`pnpm test:emulators`（既定ポートのEmulator）と同じ時間帯だった。データが03:19の保存時点に戻ったため、ユーザーの承認を得て残ったFirestoreを書き出し・停止し、`local:reset`で初期化した。
- 2回目（15:53ごろ）は、別のClaude Codeセッションが既定ポートのEmulatorを15:51〜15:53に動かした時間帯だった。その後、別の主体が15:59にローカルサーバーを起動し直し、当日の参加者・匿名ユーザー・写真が残っていた。

原因は特定していない。CLIのデバッグログは残っていなかった。**ローカルサーバーの稼働中は、別のEmulator試験を同時に動かさない**運用とする。初期化前のデータは`.tools/local-runtime/data-backup-before-reset-20261030/`、停止前のFirestoreは`.tools/local-runtime/orphan-firestore-backup-20261030/`に控えた（Git対象外）。

## 後始末

一時的な受信処理・プローブをJSから外し、生のlogcatファイルは削除した。緩めたしきい値は、アプリを8082で再起動して既定値へ戻した。AndroidのBluetoothを元のOFFへ戻した。両端末の接続先を元のMetro（8082）へ戻し、8083のMetroは停止した。**8082は疑似近接のまま**であり、nativeの試験では`PROXIMITY_MODE=native`のMetroが必要。ローカルサーバーは別の主体が起動したものを止めずに残した。

# 保存・削除方針の実装照合と検討案

作成日：2026年10月27日（日本時間）  
対象：利用文書草案セット`draft-2026-10-27.1`のL-04・L-06。関連：L-05・L-07・L-09  
状態：内部レビュー用・未承認。保存期間の新規決定、法務確認、削除機能の完成を示さない。

## 1. 今回の範囲

[製品仕様](../PRODUCT_SPEC.md)と[承認記録D-01・D-02・D-05・D-06・D-08](../IMPLEMENTATION_PLAN.md)を維持し、ローカル実装に何が保存され、何が削除されるかを照合した。利用者向けの説明は[プライバシーポリシー7・8](PRIVACY_POLICY.md)にあり、本書はそれを確定するための内部資料である。

予算0円・課金先未接続を維持する。運営者は日吉駿斗（個人運営）、住所・問い合わせ先は未定。保存期間を勝手に数値化せず、文書公開、クラウド変更、アプリ接続、削除処理の実装変更は今回行わない。

## 2. すでに決まっているルール

- 正規化写真は本人削除まで期限を設けず保存する。盤面の形・配置と端末の完成作品ギャラリーも期限を設けず保存する。容量や費用を理由に自動で30日等へ短縮しない。無地化後のピースの形・配置は残す。
- 本人削除では写真・その日の署名・キャプションを現在盤面と過去のギャラリーから取り除く。本人の当日FITと再撮影は不可。他の参加者は成長を継続できる。
- オフライン端末への削除反映は次回接続時。外部に書き出した画像は回収できない。作品全体の個別削除機能は作らない。
- 審査用元画像は処理完了後に削除する。保留案件は公開せず確認対象にする。保留のため元画像を無期限に保存する方針にはしない。
- 近接トークンは短時間で失効し、FITセッションは短期で削除する。失効後に操作を許可せず、削除待ちのセッションをFIT履歴や個人分析に使わない。
- 日次の公開識別情報は午前4時に失効する。作品・本人削除・閲覧権限に必要な非公開対応は区別して保持し、人間関係や日をまたぐ分析へ転用しない。
- 利用終了では本人写真の一括無地化と認証主体等の削除を行う。安全・法的保管例外は対象・理由・期間を確定する。端末紛失時の外部申請経路も用意する。
- アプリ削除や機種変更でMVPのギャラリー・本人用削除情報を復元する機能は追加しない。アンインストールをサーバー上の写真の削除依頼とは扱わない。

## 4. 実装上の重要な残作業

1. **写真以外のコピーを削除対象に含める。** `pieces`だけを無地化しても、`captures`、`approvals`、`reviewQueue`、旧`views`等に署名・キャプションや所有者対応が残り得る。本人削除と利用終了でどれを消し、どれを限定して保管するかを一覧で追う。検索・取得が拒否されることと、保存された内容の消去を混同しない。
2. **保留案件の終結と証拠の削除を作る。** 現状はキューがある限り保留画像を残す。完了・却下・日付失効・再確認ごとに保存の起算点を決め、保全対象以外が無期限に残らないようにする。前日の保留案件を、日付検証を迂回して当日ピースへ公開しない。
3. **削除ジョブの完了まで確認する。** 画像権限を閉じるトランザクションはあるが、本人削除の公開API・全コピーの整理・正規化画像の削除workerは完成していない。ジョブ作成を削除完了と表示する根拠にしない。
4. **利用終了を状態名だけで終わらせない。** `ended`状態の更新、Auth削除、本人写真の一括無地化、端末消去、各記録の消去・例外保管は別の処理である。順序と失敗時の再試行を決め、失効した資格で処理が再開・公開されないことも確認する。
5. **日次情報の失効と後片付けを分ける。** 4時以降のAPI拒否だけでは、前日の中間盤面や日次対応の削除は終わらない。Gallery・削除権限を壊さず、不要な情報を整理するPhase 6の作業に含める。

`cleanupCaptures`は毎時の実行予定で、一度に最大100件の期限到来ジョブを処理する実装である。これは「期限到来から1時間以内にすべて消える」という保証ではない。未配備、処理量、障害・再試行による遅延を考慮した監視・運用が残る。

## 5. 失効・表示停止と消去を区別する

| 段階                           | 意味                                                                       | 本人削除で残る確認                                               |
| ------------------------------ | -------------------------------------------------------------------------- | ---------------------------------------------------------------- |
| 操作の失効・閲覧停止           | サーバーが操作・写真取得を拒否し、最新表示を無地にする                     | 現在盤面・過去作品・FIT事前確認等のすべての取得経路              |
| 運営者の通常保存領域からの削除 | 元画像・正規化画像・文章のコピー等を対象ごとに削除する                     | 保留・合格時の入力コピー、表示コピー、再試行中の書込みによる復活 |
| 端末への反映                   | 表示、キャッシュ、Galleryの該当写真等を消す                                | オンライン端末、長期オフライン端末、途中終了、ディスク異常       |
| 委託先の保持コピーの消去       | 論理削除後に残るソフトデリート、旧世代、バックアップ、サービスログ等の扱い | 実設定と契約、期限、限定した保管・復元時の削除再適用             |
| サービス外の保存画像           | 参加者が外部へ保存・共有した画像                                           | 回収できない。削除完了の対象に含めた説明をしない                 |

FirestoreのTTLは即時削除ではなく、親文書のTTL削除だけではサブコレクションも削除されない。期限到来後の拒否はAPI・Rulesで行い、TTLの実行を待たない。[Firestore TTLの仕様](https://firebase.google.com/docs/firestore/ttl)

Cloud Storageには、削除後のオブジェクトを一定期間保持するソフトデリートがある。Storageの削除APIが成功したことだけで、保持コピーまで即時に消えたとは説明できない。実bucketのソフトデリート・世代管理・保持設定を確認し、削除要件と復旧要件を合わせて判断する。今回はbucket作成や設定変更をしない。[Cloud Storageのソフトデリート](https://docs.cloud.google.com/storage/docs/soft-delete)

認証、通知、診断等の委託サービスにも独自の情報・保持期間がある。運営者のアプリ用保存領域の削除と区別して説明する。Firebaseの一般資料に載る期間を、そのまま本サービスの約束や全サービス共通の保存期間にはしない。[Firebaseのデータ処理と保持に関する説明](https://firebase.google.com/support/privacy)

## 6. 次に決める項目

以下は未決定の一覧であり、承認済みの日数や運用ではない。先に一つずつ決め、必要な法務確認を行い、その後に実装と利用文書へ反映する。

拒否案件の結果記録と画像の保存は区別する。元画像は処理完了後に削除する仕様を維持し、拒否された元画像を証拠として新たに保管する変更は採用していない。

| 対象                                       | 決定に必要な内容                                                               | 仕様を守るための条件                                                           |
| ------------------------------------------ | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| 保留・拒否・通報の証拠と審査結果           | 審査完了／再確認終了等の起算点、通常の保管日数、重大事案の例外、担当と再点検日 | 公開しない。必要な安全対応・法的保全を壊さず、理由不明の無期限保管をしない     |
| 撮影情報と合格時の入力コピー               | どの文章をいつ消すか、冪等な再試行・同日一枚判定に必要な最小情報               | 本人削除した文章を残したまま「すべて削除済み」としない。同日再投稿の防止は維持 |
| 期限切れ・削除失敗                         | 消去完了の目標と上限、再試行・滞留通知、緊急時の担当                           | 毎時実行を上限保証にしない。失敗を放置しない                                   |
| FITトークン・セッション                    | 操作の有効時間と、失効後の物理削除の期間をそれぞれ決める                       | 短期とし、関係履歴・分析へ転用しない。Phase 5で相互検知の設計と合わせる        |
| 安全主体・ブロック・同意・問い合わせ・監査 | 必要性、利用終了後の例外、目的別の保存期間と削除、権利申請への回答             | 永続安全IDを推薦や個人別分析へ転用しない。無期限保管を初期値にしない           |
| 委託先保持・バックアップ                   | 実サービス設定、契約、保持期限、復元権限、復元後に削除を再適用する手順         | ユーザー向けのGallery復元機能とは区別する。削除済み内容を再公開しない          |

審査証拠の期間等は、運営者の日吉駿斗と専門家が確認する。処理量・OS挙動・委託先の保持等は実装担当が検証する。児童安全担当、対応時間、問い合わせ窓口はまだ確定しておらず、個人運営の指定だけで全担当を割り当てたとは扱わない。

## 7. 実装時に追加する検証

- 個別写真削除で、権限失効に加えて、画像と文章のすべてのコピーが指定の対象どおりに消える。意図的な保管例外は一般表示から分離される。
- 削除・利用終了と撮影審査・FIT・画像保存が競合しても、写真・文章・権限が復活しない。削除再試行は重複実行で壊れない。
- 保存期間を設定する際は、期限の直前・ちょうど・直後を確認する。保全対象と通常案件の期限を混同せず、解除後は通常の削除へ戻る。
- 長期オフライン端末の復帰時、削除された写真を先に表示しない。Galleryのキャッシュ・書き出しの派生ファイルの管理範囲を確認する。
- Auth削除や端末情報の消去途中で失敗しても、利用終了の処理が回復できる。権利申請の本人確認で他人の削除情報・安全識別子を漏らさない。
- 実Storageの保持設定、委託先・バックアップを含む消去の範囲、OS上の削除をstaging・実機で確認し、結果に合う利用者向け説明にする。

これらは後続実装の検証項目であり、今回追加して合格させた自動テストではない。現在のテストが画像の掃除や取得拒否に合格していても、すべてのコピーの消去・法務確認・運営の成立を合格とは扱わない。

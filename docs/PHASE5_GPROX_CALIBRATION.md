# Phase 5-5e：G-PROXの基準と混在時の近接補正

作成：2026年10月30日（日本時間）。対象はiPhone 16（iOS 26.5.2、`iPhone17,3`）とOPPO PDRM00（Android 13、広告HIGH）。状態：**合格基準案を承認し、距離別RSSIを測って混在時のしきい値と組み合わせ別の補正を決め、ソース上の値で混在FITの相互検知を確認した**。G-PROXの合格判定（各条件20回以上の試行）・他の端末の組み合わせ・Phase 5の完了ではない。BLEで正確な10cmを保証しない。

[試験計画](PHASE5_DEVICE_TEST_PLAN.md)・[5-5dの記録](PHASE5_MIXED_FIT.md)を引き継ぐ。サーバーの認可・相互一致の規則・盤面・写真の閲覧範囲・回数制限・期限は変更していない。

## 2. 測定方法

`apps/mobile/src/local/rssi-survey.ts`の測定は、サーバーの発行していないランダムなトークンでネイティブの無線を開始し、最初の3秒を捨てて20秒間を1秒窓に分ける。相手1台だけの窓の中央値（判定関数と同じ量）を集め、最小・p10・中央・p90・最大、複数候補の窓・空の窓、トークン読み取りの有無、判定が加える補正値を出す。サーバーへの報告・判定・保存は行わない。FITの無線が動いている間は押せない。

測定はD1・D2を非金属の台に置き、外装の最短間隔を定規で測った。各条件1回（20窓）で、意図した相手1台だけが見えていた（全条件で複数候補0）。集計のログは`.tools/proximity-measurements/`（Git対象外）に置き、レビュー後に削除する。

| 背面 50 cm    | −70／−69／−68／−67.5                           | −54／−53／−53／−52                             |

測定中にiPhoneが動いた1回は除外した。20 cmでは両方向とも一時的に大きく下がる窓があった。

- 同じ条件の2方向の差は14〜18 dB（中央値）で、距離によらずほぼ一定。
- 背面同士は横並びより約8 dB強い。そのため、判定の境目は「横並び10 cm（成立すべき最も弱い値）」と「背面50 cm（成立してはいけない最も強い値）」の間に置く必要がある。
- iPhone側の境目は−63〜−67.5、Android側は−45〜−52。−65／−48を選び、余裕は両側とも約2〜4 dBしかない。
- 10 cmと30 cmはiPhone側で約1 dBしか離れておらず、20〜30 cmでの成立は区別できない。GPROX-DRAFT-1は20／30 cmを観察項目としており、成立率の下限を設けていない。

この2台だけでは、差の原因がiPhoneの受信感度か、Androidの送信出力かを切り分けられない。補正は「iPhone 16がAndroidから受ける場合」だけに限定した。

## 4. 実装

| 範囲                 | 変更                                                                                                                                                                                                                                                          |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 通信形式（共通GATT） | トークン特性値＝トークン16バイト＋OS区分1バイト（1＝iOS、2＝Android）。読み手は16バイト（旧ビルド）と未知の区分を「区分不明」として受け、17バイトを超える値は従来どおり拒否する。区分はトークンと別に扱い、トークン・ハンドル・NIの結び付けには含めない       |
| iOS（Swift）         | `FitWire.tokenValue`・`tokenRecord`。観測に`peerPlatform`（トークンが読めているときだけ）。モジュール定数`model`（`utsname.machine`）                                                                                                                         |
| Android（Kotlin）    | `FitWire.tokenValue`・`platform`、`FitPeerState.platform`。観測に`peerPlatform`（トークンを渡すときだけ）。モジュール定数`model`（`Build.MODEL`）                                                                                                             |
| 判定（TypeScript）   | `src/fit/calibration.ts`の補正表（受信側の機種×送信側の区分）。`judge`は観測ごとの補正関数を受け、近接・存在の両方に補正後の値を使う。`NativeProximity`が端末内の機種から補正関数を作り、`FitController`が渡す。表にない組み合わせ・区分不明・旧ビルドは補正0 |
| 開発用の観測         | RSSI測定ボタン（§2）。結果に適用された補正値を表示する。ローカル開発版だけで、通常版へは含めない（`check:local-boundaries`で確認）                                                                                                                            |

OS区分はFIT画面を開いている間（最長45秒）、同じサービスのGATTを読む近くの端末に見える。機種名・端末ID・名前・写真・安全IDは送らない。OS種別はBLEの広告の振る舞いからも推測でき得る程度の粗い情報として扱う。機種IDは端末内の補正表の検索だけに使い、無線・サーバー・ログへ出さない。

補正0の組み合わせは成立しにくい側に倒れる。例えばiPhone 16同士がBLEだけで判定する場合、ここで測った「iPhoneが受けた値」と同程度なら成立しない可能性がある。遠距離での誤成立を補正で増やさないことを優先した。

## 5. 実機での確認

新しいビルド（iOS・Androidとも`PROXIMITY_MODE=native`のDebug、Metro 8083）で確認した。

1. 横並び10 cmのRSSI測定：iPhoneは補正+17（窓中央値の最小−65／中央−62、補正後−48／−45）、Androidは補正+0（最小−48／中央−46.25）。端末内の機種IDとGATTの区分から、設計どおりの補正が選ばれた。ただし初回の測定より2〜4 dB弱く、両側の最小値がしきい値ちょうどだった。
2. 通常のFIT画面で背面同士約10 cm：両端末で「すでに同じパズルにいます。接続は不要です。」を表示。サーバーの相互一致を経ないと出ない結果であり、5-5dのようなメモリー上の書き換えなしで、ソース上の値で混在の相互検知が成立した（2人は5-5dで同じ盤面）。
3. 背面同士50 cm：両端末とも30秒間探索中のまま、結果は出なかった。

いずれも1回ずつの確認で、成立率・誤成立率の判定ではない。

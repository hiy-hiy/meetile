# Phase 5-5c：iPhone–AndroidのGATTリンク共有

作成：2026年10月30日（日本時間）。対象は[5-5b](PHASE5_PROXIMITY_DIAGNOSTICS.md)で残った「iPhone側がAndroidのトークンを読めずpendingのまま」の調査と修正。製品のFIT条件・近接しきい値・サーバー認可・広告内容・GATT形式・権限は変更しない。距離精度・G-PROXの合格判定は含まない。

## 原因

実機（iPhone 16／iOS 26.5.2、OPPO PDRM00／Android 13）で、5-5bと同じ人工トークンの通信プローブを再実行して再現した。iPhoneは約23秒で237件の観測を受けたが、トークン付きは0件。AndroidはiPhoneのトークンを読めていた。

Androidのlogcat（Bluetoothスタックの記録のみ。トークン・アドレスは記録へ残していない）で次を確認した。

- LEリンクは`link_role=0`（Androidがcentral）の1本だけ。iPhoneからAndroidへのリンクは一度も作られなかった。
- そのリンク上で、iPhoneからはOSのサービス探索要求だけが届き、ATT Read Requestは0件だった。

iPhoneは広告と接続に同じアドレスを使う。Androidが先にそのアドレスへ接続すると、iPhoneからAndroidの広告アドレスへの接続は成立せず、iOS側は5秒のtimeoutと再接続を繰り返していた。Androidの広告アドレスと接続元アドレスは異なるため、既存リンクをiPhoneから使うと、iPhoneには同じAndroidが2つの候補として見える（下の検証2）。

## 修正

| 端末    | 変更                                                                                                                                                                                                                                                                  |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Android | 新しく見つけた相手への自発的な接続を2秒待つ（`FitConnectOrder`）。その間に相手から接続されたら、そのアドレスへすぐ`connectGatt`し、既存リンク上でGATT clientを動かす。待っても接続されなければ従来どおり自分から接続する。広告・探索・GATT serverは待たずに開始する。 |
| Android | GATT操作の期限のうちサービス探索だけを3秒から10秒へ延長。iPhoneがcentralのとき、iPhoneのGATT全体の探索が3秒を超えて切断されていた。ほかの操作は3秒のまま。                                                                                                            |
| iOS     | 自分のトークン特性を読みに来たcentralを`retrievePeripherals(withIdentifiers:)`で取得し、既存リンク上でトークンを読む（Androidが先に接続できた場合の予備経路）。観測の送信は従来どおり実際のscan・`readRSSI`のRSSIを伴うときだけ。保持期限の延長には観測値を作らない。 |

予備経路で同じAndroidが2候補に見える場合、トークン未読の候補が残るため、既存の複数候補判定がFIT報告を止める。誤った成立ではなく不成立側に倒れる。未読候補を推測で隠す・統合する処理は追加していない。

広告への識別子追加や、接続役割を決める新しいGATT特性は採用しなかった。広告はサービスUUIDだけとする既存の設計と、iOS／Androidの共通GATT形式を維持するため。

## 実機での確認（人工トークンの通信プローブ）

5-5bと同じ方法で、Metro（8082）のinspectorからネイティブモジュールを直接開始・停止した。サーバーのFIT操作・撮影・年齢確認・開始同意は行っていない。プローブは確認後にJSグローバルから除去し、AndroidのBluetoothを元のOFFへ戻した。

| 検証                | リンク                                 | iPhoneの候補・トークン付き観測   | Androidの候補・トークン付き観測 |
| ------------------- | -------------------------------------- | -------------------------------- | ------------------------------- |
| 1. 修正前           | Android→iPhoneの1本                    | 1候補・237件中0件                | 1候補・617件中583件             |
| 2. iOSの修正のみ    | Android→iPhoneの1本、Read Request 40件 | **2候補**（未読203件／既読20件） | 1候補・既読                     |
| 3. 両方の修正       | iPhone→Androidの1本                    | 1候補・261件中245件              | 1候補・603件中416件             |
| 4. 同時開始×2回     | iPhone→Androidの1本                    | 1候補・初回トークン1.6・1.7秒    | 1候補・初回トークン3.5秒        |
| 5. Android先・5秒差 | iPhone→Androidの1本                    | 1候補・iPhone開始から1.6秒       | 1候補・iPhone開始から約3.8秒    |
| 6. iPhone先・5秒差  | iPhone→Androidの1本                    | 1候補・Android開始から約1.5秒    | 1候補・Android開始から3.5秒     |

検証3では、Androidのサービス探索がiPhoneのGATT全体で3秒を超え、一度切断されて最初のトークンまで約7秒かかった。探索期限を延ばした後の4〜6では切断がなかった。停止はどの回も応答し、AndroidのOSログで広告停止・GATT切断を確認した。

これは**双方向のトークン取得を確認しただけ**であり、相互検知・双方確認・サーバーFIT・距離精度・誤接続率の合格ではない。RSSIは近距離の机上で取得した値で、しきい値の判定には使わない。

## 未確認・制限

- Android同士：2台目がなく未確認。双方が2秒待ってから接続するため、トークン取得が約2秒遅れる見込み。
- iPhone同士：2台目がなく未確認。iOSの予備経路は同じ識別子に統合される想定だが、実機では見ていない。
- iPhoneが2秒以内に接続できない環境（混雑・遮蔽・3台以上）では予備経路に入り、上記の2候補によりFITが止まり得る。3台以上の検出と合わせて別途確認する。
- 他機種・Android 12、14〜16は未確認。今回のAndroid 13だけで全範囲を代替しない。
- 2秒の猶予と10秒の探索期限は開発用の初期値で、G-PROXの基準ではない。

## 検証

- `pnpm test:proximity:ios`：iOS SDK型検査・共通GATT形式試験が成功。
- `pnpm test:proximity:android`：20件成功（追加2件：接続開始の猶予、探索期限）。
- iOS Debugの署名付きビルド・iPhone 16への更新インストール、Android Debugビルド・Android 13への更新インストールが成功。
- 整形・Lint・TypeScript型検査：成功。`pnpm test`：110＋169＋18件の計297件成功。`pnpm test:emulators`：115件成功。`pnpm check:local-boundaries`：通常版のiOS／AndroidバンドルとFunctionsにローカル専用コードが含まれないことを確認。JS・サーバーの変更はないため回帰確認として実行した。

編集前のネイティブとドキュメントを`.tools/phase5-5c-baseline/`へ保存して差分を確認した。仕様原本・AGENTS.md・承認済み計画のハッシュは不変。

**5-5dでの追加**：通常のFITでは約30秒ごとのトークン更新でAndroidの広告アドレスが変わり、更新をまたいで残ったリンクのためにiPhoneが同じAndroidを2候補として見ていた。iOSの切断条件とAndroidの再利用条件を追加した。詳細は[5-5dの記録](PHASE5_MIXED_FIT.md)。
